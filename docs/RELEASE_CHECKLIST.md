# 커밋·공개 서비스 동기화 절차

GitHub push와 공개 서비스 배포는 별개입니다. 이 저장소의 CI는 검사만 수행하며 공개 서버를 갱신하지 않습니다.

1. 대상 커밋을 고정합니다: `git rev-parse HEAD`. CI 테스트·노트북·빌드 결과가 모두 성공했는지 확인합니다.
2. 실제 데이터가 있는 실행 환경에서 `python scripts/deploy/release.py --verify-only`로 집계·입력 일치를 확인합니다. 새 입력이면 README 순서대로 정규화·집계·근거를 먼저 생성합니다.
3. 배포 담당자가 대상 환경과 릴리스 커밋을 기록하고 해당 환경의 배포 절차로 프론트엔드·API·정적 집계를 함께 반영합니다. 이 공개 링크의 호스팅은 GitHub 자동 배포 대상으로 설정되어 있지 않습니다.
4. 새 브라우저 세션에서 README 공개 링크를 열어 도시 선택, 4개 챕터, 후보 교차 근거, 수요 비교, 자료 준비 상태, AI 선택 맥락을 각각 확인합니다. React의 페이지 파일 수와 공개 메뉴 수를 동일성 기준으로 사용하지 않습니다.
5. FastAPI를 직접 배포한 경우에만 `python scripts/deploy/release.py --verify-only --check-url https://YOUR_API_ORIGIN`을 실행합니다. 공개 페이지 주소를 FastAPI API 주소로 대신 사용하지 않습니다.
6. docs/DEPLOYMENT_STATUS.md에 확인 시각(UTC), 공개 URL, 저장소 커밋, 실제 배포 커밋(확인 불가하면 미확인), 확인한 기능·미확인 기능·배포 담당자를 남깁니다.
7. 불일치가 있으면 완료로 표시하지 않고 재배포 또는 공개 안내를 갱신합니다. 이전 정상 릴리스와 데이터 버전을 보존합니다.

## 배포 기록 양식

- 확인 시각:
- 검증한 저장소 커밋:
- 배포된 커밋 / 확인 근거:
- 공개 URL:
- 배포 담당자:
- 실제 데이터 준비 검사:
- 브라우저 기능별 결과:
- 미확인 사항 / 후속 작업:

비밀키를 CI에 추가하거나 서버 자동 배포 권한을 부여하는 변경은 포함하지 않습니다.
