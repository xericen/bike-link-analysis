## 1. 원본부터 수행한 Spark 검증

SQLite 집계를 Spark로 다시 더한 이전 실험과 다르다. 이번에는 **원본 ZIP의 CSV 내용**을 읽었다.

- Python은 ZIP 추출·문자 인코딩 변환·입력 파일 선택과 정답 DB 대조만 담당했다.
- Spark4.1.4가 문자열 정리, ID·시간·이용시간 유효성 검사, 관제센터 제외, 중복 제거, 일별 OD와 시간대별 대여·반납을 계산했다.
- 세종의 같은 월·순번에 서로 다른 내용이 있으면 임의로 첫 행을 선택하지 않고 중단하도록 했다.
- 정규화 결과의 실제 출발·도착 ID로 앵커 인근 여부와 위치 미연결 시간대 집계도 Spark에서 재계산했다.
- Spark 출력과 읽기 전용 기존 SQLite를 행 수·수량 합계·키/수량을 포함한 SHA-256 네 개64비트 구간의 합으로 대조했다. 순서에 무관한 다중집합 지문 검사이며 충돌 가능성이 수학적으로0인 완전 증명이나 파일 바이트 동일성 주장은 아니다.

| 도시 | 보유 기간 | 원본 CSV | 원본 행 | 유효 이용이력 | 제외 | 중복 |
|---|---|---:|---:|---:|---:|---:|
| 서울 | 2025-01~12 | 12 | 37,372,654 | 37,176,546 | 196,108 | 0 |
| 대전 | 2024-08~2026-10 | 27 | 15,805,248 | 14,992,420 | 789,067 | 23,761 |
| 세종 | 2020-01~2025-12 | 24개 분기 | 12,903,600 | 12,903,589 | 11 | 0 |
| 합계 | 도시별 보유 기간 | 63 | 66,081,502 | 65,072,555 | 985,186 | 23,761 |

합계는 처리량이며 동일 관측기간의 도시 비교 이용량이 아니다. 관측일이 없는 날을0으로 채우지 않았다. 기존 전체 도시 공통12월과 개별 도시 조회 범위도 변경하지 않았다.

| 도시 | 일별 OD 행 | 시간대 대여·반납 행 | 연계/미연결 시간대 행 | 기존 DB 대조 |
|---|---:|---:|---:|---|
| 서울 | 20,994,451 | 15,509,697 | 8,760 | 세 출력 모두 일치 |
| 대전 | 10,773,929 | 9,590,510 | 18,670 | 세 출력 모두 일치 |
| 세종 | 10,082,096 | 9,929,007 | 52,280 | 세 출력 모두 일치 |

원본부터 OD·대여반납 대조까지의 실행 시간은 서울1,472.34초·대전706.09초·세종517.30초였다. 여기에 연계 시간대 대조를 별도로 실행했다. 이 시간에는 추출·캐시·SQLite 기준 지문 계산이 포함되므로 순수 Spark 처리 속도나 pandas 대비 성능으로 해석하지 않는다. 단일 서버local[2] 실험이다.

지문 JSON의 `station_usage.actual.trips`는 대여+반납 **작업 수 합계**이며 실제 이동 건수가 아니다. 실제 유효 이동 건수는 `valid_rows`와 OD의trip_count 합계로 확인한다.

원본SHA-256과 파일별 인코딩·행 수·제외·중복 기록은 [원본 목록](completion-20261123/raw-sources.json)과 `completion-20261123/raw-pieces/`에 보존했다. 기존 운영 DB와 정규화 진입점은 그대로이며, 별도 Spark 검증 파이프라인이 같은 결과를 산출한 것이다.

## 2. 동일 원점·도착지의 시간표 기반 여정

[대전교통공사 공식 사이버스테이션](https://www.djtc.kr/kor/cyberStation.do)에서 역별 평일 시간표와 구간별 예상 소요시간을 실제 확보했다. 공개 화면이 사용하는 JSON 요청 주소·응답SHA-256·수집일은 결과에 기록했다.

기존 대전2·3·4순위 후보에서 출발해 같은 승차역을 거쳐 **반석역 지상 출구**에 도착하는 두 경로를 비교했다.

1. 도보 접근 → 역 진입 → 다음 열차 대기 → 지하철 → 출구 이동
2. 자전거 접근·반납·도보 연결 → 역 진입 → 다음 열차 대기 → 지하철 → 출구 이동

출발시각은 평일08:00·08:15·18:00이다. 대여·반납2분, 역 진입·출구 각2분은 관측값이 아닌 가정이며 대여·반납0/2/5분과 진입1/3/5분의 민감도를 별도 계산했다. 정부청사에서 끝나는 열차를 반석까지 가는 열차로 사용하지 않았다. 막차 이후에는 이용 가능으로 대체하지 않는다.

대전 기존2순위는 접근 구간에서 자전거가 약3.895분 느리지만08:15 출발 시 같은 열차를 타 **최종 도착시간은 같다**.08:00·18:00에는 다음 열차를 타6분 늦는 모델 결과가 나왔다. 접근시간 차이와 전체 여정 도착시간 차이가 항상 같지 않다는 사례다.

기존3·4순위의 큰 단축값은 현 OSM 도보 우회의 영향을 받는다. 실제 수십 분 절약 효과로 확정하거나 설치 순위를 바꾸지 않는다.

**범위:** 현행 시간표·현재 OSM·가정한 역 내부 이동을 결합한 대표 예시다.2025년 실제 운행을 재현한 것이 아니고, 철도 간 환승 없는 한 노선이므로 환승 횟수·철도 간 환승 대기는0이다. 다중노선 환승을 검증했다는 뜻은 아니다.

[세종 B2 공식 시간표](https://www.sctc.kr/www/conts/view.do?mnucd=140)도 실제 확보했다.2025-10-24 시행과 월드컵경기장 연장을 확인했지만 중간 정류장 도착시각이 없어 반석역 지하철 도착시각과 임의로 합치지 않았다. 기존2025년7월 BRT 자료와 노선 구조가 달라졌다는 점도 확인했다.

웹·React의 **분석 결론 → 대전 → ‘대기시간까지 포함하면?’**에서9개 비교 행을 볼 수 있다.

## 3. 원격 자료와 실제 현장 검증의 구분

- 세종에는 이전에 다른 도시에서 소진됐던 조회 예산과 별도로12회의 경로 요청을 수행했다. 상위5후보 중 시간상 유리한 연결을 확인한 곳은 여전히1곳이다. 미확인 경로를 실제 불가능이나 효과0으로 바꾸지 않았다.
- 서울5후보의 반납 대여소는 공식2026년6월 마스터와 **이름 일치·좌표5m 이내·유일 매칭**을 모두 만족했다. ST-398(QR15),ST-243(QR8),ST-2005(QR20),ST-1317(LCD22),ST-579(LCD20)의 거치대 열을 확인했다.
- LCD·QR의 빈 열을0으로 만들거나 임의로 합산하지 않았다. 이는 해당 시점의 마스터 정보이며2025년 용량·현재 실제 재고·신규 부지 설치 허가가 아니다.
- 웹·React의 **분석 결론 → 서울 → ‘반납 대여소의 공식 거치대 정보’**에 표시했다.

[서울 실시간 대여정보](https://data.seoul.go.kr/dataList/OA-15493/A/1/datasetView.do)와 [대전 타슈정보 API](https://www.data.go.kr/data/15109253/openapi.do)의 존재·인증 요건을 확인했다. 관련 인증키는 현재 환경에 설정되어 있지 않았다. 이 API들의 실시간 현황을2025년 과거 재고로 대체하지 않았다.

현장 방문 기록·부지 사용 권한·시점별 재고·설치 전후 실측은 확보되지 않았다.15후보의 [현장 확인 등록표](completion-20261123/field-evidence-register.csv)에 필요한 항목을 남겼으며 전부 **현장 미검증**이다. 실측값과 설치 효과를 만들어 넣지 않았다. 현재 질문에 대한 현장 기록 요청에도 최종 기록 시점까지 제공된 내용은 없다.

## 4. Solar 원문 검사와 비용 제한

### 실제 응답을 다시 검사한 결과

추가 유료 실행은 세 도시 질문을 두 차례씩 수행한6질문·공급자12호출이었다. 첫3응답이 출력 길이 제한에 걸려 짧은 결론 지시로 보완했고, 이후 추가 유료 재시도 없이 저장된 응답으로 검사를 확대했다.

처음의 전역 숫자 존재 검사만으로는 실제 오류를 놓쳤다. 원문과 서버 필드를 직접 대조해 다음을 확인하고 검사에 추가했다.

| 실제 원문 | 발견한 오류 | 처리 |
|---|---|---|
| 서울 | 기본 도보20.7467분 자리에 연계 시간12.32분 사용 | 순위·앵커 이름으로 지칭한 경우도 필드 대조 후 보류 |
| 대전 | 양수70.28분 단축을 ‘크게 느림’으로 해석 | 단축값 부호와 빠름/느림 서술 대조 후 보류 |
| 세종 | 원본grid ID를격자로 변형,2분 가정의20.9983분을5분 가정으로 서술 | 원본ID·가정별 값 연결 대조 후 보류 |

실제3원문은 최종 검사 재생에서 모두 보류됐다. 기본 본문은 서버 도구값 요약이며 원문은 `solar_answer`, 보류 근거는 `completion_validation`에 분리한다. 모델이 사실을 모두 맞혔다는 성공 사례로 보고하지 않는다.

[111개 통제 문장](completion-20261123/solar-replay.json)은 후보 간 값 바꾸기, 단위·면적·기본 시간, 시간 가정, ID 변형, 미확인 경로, 실제 환승·설치 효과 단정을 검사했고111/111 기대 결과와 일치했다. 실제3응답 평가와 구분한다. 오류를 발견해 만든 회귀 세트이므로 외부 독립 평가나 모든 자유 서술의 정확도 증거가 아니다.

### 입력·출력과 비용

- 서버의 원래evidence는 보존하고, 모델에 전달할 때 긴 반복 설명·상세 배열을 명시적으로 생략한다. 생략한 값을 추측하도록 하지 않는다.
- 도구별 입력은24,000UTF-8바이트 기준으로 축약하며 그래도 크면 상세 수치를 보류한다.
- 도구 정의를 포함한 **각 공급자 요청100,000UTF-8바이트 상한**을 첫 호출 전과 최종 호출 전에 검사한다. 초과하면 추가 호출을 막고 가능한 경우 서버 요약으로 표시한다.
- 한 질문의 공급자 요청은 도구 선택·최종 답변2회, 출력 상한은 각각550·600토큰, 자동 재시도는0회다.
- 이것은 입력/출력 제한이며 실제 원화 요금의 고정 상한은 아니다.

같은 세 질문의 기존 저장 기록은203,077토큰, 이번 최종 세 질문은45,353토큰으로 관측됐다(약77.7% 감소). 두 차례 추가 실행의 총 사용량은81,695토큰이다. 이후 추가한 엄격한 입력 상한·원문 검사·기간 구분은 저장 응답 재생과 회귀 테스트로 검증했고 추가 유료 호출은 하지 않았다. 모델이 고른 도구와 답변 길이도 달라져 입력 축약만의 인과 효과로 해석하지 않는다. [실측 기록](completion-20261123/solar-cost.json)에 원문과 한계를 남겼다.

## 5. 검증과 보존

- 백엔드 테스트 **232개 통과**, 기존 경고40건.
- React TypeScript·프로덕션 빌드와 web 빌드 통과.
- 공개 웹·React에서 PC1440px·모바일390px의 여정9행·거치대5행 표시, 가로 문서 넘침·페이지 오류 없음. 기존 디자인은 유지하고 펼침 표와 결론 근거만 보완했다.
- 기존 공통5파일(analysis.sqlite,kpi_cache.sqlite,stations.csv,station_usage.csv,kpi_inputs.json)의SHA-256 불변. 개별 DB도읽기 전용으로 열었다.
- 원본·사전 집계 DB 삭제·초기화·재생성 없음. 별도 서버 재시작·배포 명령·Git 커밋·푸시 없음.
- 현재 web 프로젝트의 빌드·동적 API가 공개 서비스에서 읽히는 것을 확인했다.
